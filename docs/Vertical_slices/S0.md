## Concepts

### Processes, users, permissions
- A **process** runs **as a user** (a uid; yours is 1000). Most of Axon's security is "what may a process running as uid 1000 do?"
- **Permission bits:** read/write/execute for *owner*, *group*, *others*, written in octal. `0600` = owner read+write only. `0644` = everyone can read.
- **Environment variables** are inherited by every child process, which is why the rules keep them for secrets and paths only, and why the command guard (S2) rebuilds the child's environment.

### Cargo workspace, crates, library vs binary
- A **crate** is the unit of compilation: a **library** (`src/lib.rs`) or a **binary** (`src/main.rs`, has `fn main`). A **workspace** shares one `Cargo.lock` and one `target/`.
- **Keep `main.rs` to ~10 lines** (load config, call the library). Tests can only reach library code; that gap hid real bugs in the old project.
- **Crate boundaries enforce the architecture:** if `daemon` doesn't depend on `orchestrator`, it can't call it. Only `shared` is shared.
- Use `edition = "2024"`.

### Where files live
| Kind | systemd variable (service) | XDG default (your user) | Axon puts there |
|---|---|---|---|
| Config (human-edited) | `CONFIGURATION_DIRECTORY` | `$XDG_CONFIG_HOME/axon/<app>` → `~/.config/axon/daemon` | `config.toml`, `policy.toml` |
| State (program-written, kept) | `STATE_DIRECTORY` | `$XDG_STATE_HOME/axon/<app>` → `~/.local/state/axon/daemon` | database, keys, journal |
| Runtime (gone at logout) | `RUNTIME_DIRECTORY` | `$XDG_RUNTIME_DIR/axon/<app>` → `/run/user/1000/axon/daemon` | Unix sockets |

- **One subfolder per binary** (`<app>` = `daemon`, `orchestrator`, `desk`, `cli`), so their files never mix: the daemon's and the desk's keys sit on the same machine as the same user, and the sandbox can deny `axon/desk/` as a whole. Only the XDG default gets the subfolder; explicit and systemd paths are already specific to one binary.
- **Resolution order:** an explicit path in the config file, else the systemd variable, else the XDG default. The config file itself can't name its own location, so its explicit step is the `--config <file>` flag. The systemd step is what lets the orchestrator run later as a dedicated system user (`DynamicUser=yes`), which has no home directory, with no code change.
- The `directories` crate finds the XDG defaults. `state_dir()` returns an `Option` because not every OS has one: understand why before handling it.

### One `Config`: serde + TOML
- `#[derive(Deserialize)]` + the `toml` crate fill a struct from a file; no hand parsing.
- `#[serde(deny_unknown_fields)]`: a typo is an error, not silently ignored (**fail closed**).
- `#[serde(default)]`: a missing field gets a default you chose on purpose.
- Loaded once, in one place, then passed down as an argument. No module reads files or env on its own.

### Secret permissions
- Reading the mode needs the trait `std::os::unix::fs::PermissionsExt`: importing a trait adds methods (`.mode()`) to an existing type.
- The check is a bit mask on the group and others bits. Work out the mask yourself.
- **Create with the right mode in one step** (`std::os::unix::fs::OpenOptionsExt::mode`), never "create, then chmod": in between, the file exists with default permissions. That gap is a **race**; you'll meet the same shape in S1 (TOCTOU) and S7.
- S0 has no secrets yet (keys arrive in S6). You build and test the function now; later slices call it.

### Errors
- `Result<T, E>` + `?`. One `thiserror` enum per layer (e.g. a config error enum with read / parse / insecure-permissions variants).
- The library returns **typed** errors; only `main` or a UI turns them into sentences. That's what lets S1 show different text to the model, the log and you.

### Tests & CI
- **Unit tests** in the same file (`#[cfg(test)] mod tests`); **integration tests** in `<crate>/tests/`, which only see the public API. (Different from the old single `tests` crate: simpler while learning. Worth a short ADR.)
- `tempfile::tempdir()` gives each test its own folder, deleted afterwards.
- CI = a GitHub Actions workflow running the three commands on every push.

## Steps (each one ends with fmt + clippy + test green)
1. Create the repo, `rust-toolchain.toml`, `.gitignore` (`target/`).
2. Root `Cargo.toml` with `[workspace]` and the 5 members; empty `lib.rs` everywhere, `main.rs` for the 4 binaries.
3. CI workflow. Push, see it green.
4. Path resolution (decide where it lives: `shared` is the natural place, since daemon and orchestrator both need it). Test each step of the resolution order.
5. `Config` for one binary (start with the daemon), with a test that an unknown field is refused.
6. Secret-file functions: create-as-0600 and load-with-check. Tests: `0600` accepted, `0640` and `0644` refused, missing file gives a clear error variant.
7. `Agent.md` for the new repo.
8. ADR 01

Bring each step for review before the next; small steps are easier to review and to learn from.

- Whether binaries use `anyhow` in `main` for the final error report, or keep `thiserror` everywhere.

## ADR 01 outline: threat model
Answer each in your own words; one page is enough.
1. **Assets:** what is worth protecting? (Files, keys, the ability to run commands, conversations, your desktop session.)
2. **Adversaries and how they act:** injected text the model reads; someone on the network; a compromised orchestrator; malicious code inside a repo you build; Telegram.
3. **Trust boundaries:** [ARCHITECTURE §4](../ARCHITECTURE.md#4-trust-model) restated: who is trusted for *actions*, who for *data*.
4. **Assumptions and out of scope:** e.g. "malware already running as my user is out of scope in V1" (and what would change that: the guardian/executor split, [Q4](../OPEN_QUESTIONS.md#q4-splitting-the-daemon)).
5. **Open questions:** [OPEN QUESTIONS](../OPEN_QUESTIONS.md) Q1–Q3. Name them; don't solve them yet.

## What the review will check
- `main.rs` is thin; logic sits in libraries.
- No `unwrap()` where the failure is possible in real use.
- No create-then-chmod.
- Tests write only inside a `tempdir`.
- Errors are typed; text appears only at the edge.
- `deny_unknown_fields` on every human-edited config.
